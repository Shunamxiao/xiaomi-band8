# 小米手环8 自建控制方案（架构设计）

> 目标: 自研 APK + 自建服务端, 直连小米手环8, 实现自定义通信、通知推送、表盘/页面内容定制
> 设备: Xiaomi Smart Band 8 NFC (m66nfc, MAC AA:BB:CC:DD:EE:FF)
> 配套手机: MI 8 (root, Android 10, Termux + SSH)

## 一、能力边界（先给结论）

| 能力 | 可行性 | 依据 |
|------|--------|------|
| 自定义通知推送（标题/正文/图标/时间） | 可做 | NoticeModule 已定位, 协议可复现 |
| 手环设置（亮度/勿扰/抬腕/闹钟/久坐提醒） | 可做 | SettingsModule/AlarmModule 已定位 |
| 电量、查找手环、震动、音乐控制 | 可做 | Battery/FindDevice/MotorVibrate/Music 模块已定位 |
| 自定义表盘安装 | 可做（需认证通过） | DialModule + 已握有的 authkey/encrypt_key |
| 手环内第三方小程序 | 条件性可行 | 官方为签名+审核制; 侧载需绕过签名校验, 未验证 |
| 刷第三方固件/重装系统 | 基本不可行 | 固件签名 + 无公开 bootloader 解锁; OTA 通道仅接受官方签名包 |
| 获取原始传感器数据流 | 可做（工作量最大） | 需逐个复现数据同步模块与 protobuf 解析 |

**技术判断**：不要走"刷机"路线。收益低、风险高（变砖）、且没有社区固件基础。所有你要的"页面展示定制"都能通过 **表盘替换 + 通知 + 事件提醒** 三个通道实现，无需改固件。

## 二、已确认的协议事实（一手证据）

见 `docs/mi-band8-protocol-analysis.md`。补充本轮新增证据：

1. **GATT 实际布局**（PC 端 BLE 实测）
   - 服务 0xFE95 下存在 0x0050~0x005A 共 11 个特征，全部 write+notify
   - 0x0050 为只读版本特征（当前值 `00 02 45 ...`）
2. **分帧协议**（jadx: `o9j / ol3 / pno / mno / k0 / d96`）
   - `[seq u16 LE][type u8][...]`，type 0/1/2/3 = CMD/ACK/SINGLE_CMD/SINGLE_ACK
3. **握手实测**：向 0x53 写入
   `00 00 02 00 04 00 02 02 <公钥>` 后，手环回 `00 00 03 00`
   （SINGLE_ACK, status=0）→ **帧格式正确、通道可用**
4. **曲线修正**：native 库 `libdevice-encrypt.so` 中的曲线参数匹配
   **sect163r2 (NIST B-163)**，公钥 48B；此前从 Java 层推测的 P-256 是错的
   （Java 层 `itn.j()` 是另一条业务路径，不是手环认证曲线）
5. **会话密钥**：HKDF-HMAC-SHA256，info=`miwear-auth`，64 字节拆 4 段
6. **设备凭据**（root 从 device_db 读到）：
   `encrypt_key = 0123456789abcdef0123456789abcdef`、`irq_key`、`token`、`sn`

## 三、三套架构方案对比

### 方案 A：完全自研协议栈（推荐长期）
我们的 APK 直接实现 BLE + 帧 + 认证 + AES-CCM，服务端只做配置与数据汇聚。

- 优点：无依赖官方 App，可控性最强，可上架/分发
- 缺点：认证细节还需 1~2 轮实证（签名流程 + 模块 ID 位置）
- 工作量：协议核心 3~5 天，业务模块按需 0.5~1 天/个

### 方案 B：root Hook 官方 App 复用其会话（最快见效）
用 Frida/Xposed 在 `com.mi.health` 进程内导出其已认证的 BLE 通道，通过本地 Socket/HTTP 暴露给我们的 App。

- 优点：1~2 天可用，天然覆盖全部官方能力（含表盘、OTA）
- 缺点：依赖 root + 官方 App 常驻；升级易失效；不适合对外分发
- 适用：先跑通产品形态、验证交互设计

### 方案 C：混合（推荐落地路径）
Phase 1 用 B（快速验证），Phase 2 换成 A（自研，去依赖）。
两者共用同一套上层 API 与 UI，只替换传输实现。

## 四、推荐系统架构

```
┌──────────────────────────────┐
│  自研 Android APK (Kotlin)   │
│  ├─ 通知转发 (NotificationListener)
│  ├─ 配置 UI / 表盘管理
│  └─ 本地 BLE 客户端 (BouncyCastle)
└──────────────┬───────────────┘
               │ HTTPS / WebSocket
┌──────────────▼───────────────┐
│  自建服务端 (小米8 Termux)    │
│  ├─ 设备/配置管理 (SQLite)
│  ├─ 消息队列 (通知/提醒/表盘任务)
│  ├─ 数据汇聚 (健康数据 API)
│  └─ 对外 REST + WS, 监听 :: 8801
└──────────────────────────────┘
```

**关键设计决策**
1. **BLE 连接放在 APK 里，不放服务端**。手环只允许一个主机连接，服务端在手机上转发会增加一跳和故障面；APK 直连延迟最低。
2. **服务端只做"配置与数据"**，不做实时链路。断网时 APK 仍能推送通知。
3. **加密用 BouncyCastle**：原生支持 sect163r2、AES-CCM、HKDF，避免自己实现二元域椭圆曲线。
4. **认证密钥本地存储**：首次配对时从官方 App 数据库导入（root 一次性），之后 APK 独立使用（注意 16 字节 key 存 Android Keystore 加密）。

## 五、接口设计（服务端 ↔ APK）

```
GET  /api/v1/device            -> 设备信息、电量、连接状态
POST /api/v1/notify            -> {app, title, text, time, icon} 推送通知
POST /api/v1/reminder          -> 事件提醒（可带自定义页面字段）
GET  /api/v1/watchface         -> 表盘列表 / 下载地址
POST /api/v1/watchface/apply   -> 应用表盘
GET  /api/v1/health/summary    -> 健康数据汇总
WS   /ws                       -> 实时状态与命令回执
```

## 六、实施里程碑

| 阶段 | 内容 | 验收标准 |
|------|------|----------|
| M1 | 协议客户端跑通认证 | 能收到手环返回的 16B 随机数 + 48B 公钥 |
| M2 | 会话加密通道 | 能读到电量（Battery 模块应答解密成功） |
| M3 | 通知推送 | 手环屏幕显示自定义标题/正文 |
| M4 | 设置与震动/查找 | 常用设置项可控 |
| M5 | 表盘替换 | 自定义表盘安装成功 |
| M6 | 服务端 + APK 联调 | 服务端下发配置，APK 执行并回执 |
| M7 | 小程序可行性验证 | 判定能否侧载（不承诺） |

## 七、当前阻塞与下一步（明确）

**阻塞点**：M1 的认证应答。我们发出的 `[04][apiLevel][02][公钥]` 只得到 ACK，
没有数据回包。原因是模块路由信息缺失 —— 应用层帧里还需要携带 **module id (130)**
与 dataType 的正确取值，这部分需要从 `ChannelApiImpl` 的 `z3` 头字段顺序确认。

**下一步（按优先级）**：
1. 反编译核对 `d1.a(int flag, int sessionId, int index, int moduleId, byte[] data)`
   的字节序与位置，补齐帧头
2. 用 `adb shell` 在手机上以 root 运行 `frida` 附加官方 App，hook
   `ChannelApiImpl.transport` 直接打印真实发送帧（比 logcat 可靠）
3. 拿到真实帧后，1:1 对齐我们的编码器，M1 即可闭环

## 八、风险清单

- **认证失败风险**：手环可能只接受"绑定关系仍有效"的会话；重新绑定会挤掉官方 App
- **固件升级风险**：升级后协议版本/曲线可能变化，需保留降级路径
- **合规风险**：仅限自有设备自用；分发需评估商标与协议逆向的法律边界
- **稳定性**：MIUI 会杀后台，需要前台服务 + 电池白名单；ESP 类断连需重连状态机
